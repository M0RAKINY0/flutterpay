FlutterPay

A learning clone of Flutterwave. Merchants get API keys, create payments, send customers to a hosted checkout page, verify the result, and receive signed webhooks. A fake bank stands in for Visa, Mastercard and the banks, so no real money moves.

TypeScript Node + Express SQLite + Prisma Naira only, in kobo Fake money only

The main flow

One payment, end to end

Create a payment through the API or SDK, open its checkout link, then verify it. A test receiver checks webhook delivery without a separate shop application.

sequenceDiagram
  autonumber
  actor C as Customer
  participant S as API request or SDK example
  participant A as FlutterPay API
  participant P as Checkout page
  participant B as Fake bank
  participant W as Webhook test receiver
  C->>S: Create a test payment
  S->>A: POST /v1/payments (secret key, tx_ref, amount)
  A-->>S: { id, link }
  S-->>C: Open checkout link
  C->>P: Enter test card
  P->>B: Charge 500000 kobo
  B-->>P: Approved, OTP needed
  C->>P: Enter OTP
  P->>A: Mark transaction successful
  P-->>C: Redirect to configured test callback URL
  C->>S: Verify the transaction ID
  S->>A: GET /v1/transactions/:id/verify
  A-->>S: { status: successful, amount, tx_ref }
  A--)W: Webhook: charge.completed (signed)
  W-->>A: 200 OK
Rules for a transaction

Payment states

A transaction can only move along these arrows. Once it is successful or failed, it never changes again. That one rule stops a lot of bugs, like a customer getting charged twice.

stateDiagram-v2
  [*] --> pending: merchant creates payment
  pending --> awaiting_otp: card accepted, OTP sent
  awaiting_otp --> successful: correct OTP
  awaiting_otp --> failed: wrong OTP 3 times
  pending --> successful: card needs no OTP
  pending --> failed: bank declines
  pending --> abandoned: nobody paid in 30 min
  successful --> [*]
  failed --> [*]
  abandoned --> [*]
Database

What gets stored

Four tables. Money is stored as whole kobo (₦5,000 is 500000) because decimals in computers round badly, and in payments a rounding bug is a missing naira.

erDiagram
  MERCHANT ||--o{ API_KEY : has
  MERCHANT ||--o{ TRANSACTION : receives
  TRANSACTION ||--o{ WEBHOOK_DELIVERY : triggers
  MERCHANT {
    string id
    string business_name
    string email
    string password_hash
    string webhook_url
    string webhook_secret
  }
  API_KEY {
    string id
    string merchant_id
    string kind "public or secret"
    string prefix "fp_sec_test_ab12"
    string key_hash
    datetime revoked_at
  }
  TRANSACTION {
    string id
    string merchant_id
    string tx_ref "unique per merchant"
    int amount_kobo
    string currency "NGN"
    string status
    string customer_email
    string card_last4
    string redirect_url
  }
  WEBHOOK_DELIVERY {
    string id
    string transaction_id
    string event "charge.completed"
    int attempt
    int response_code
    datetime next_retry_at
  }

FlutterPay never stores a full card number, only the last 4 digits. Real processors follow the same rule.

Roadmap

Build order

Eight phases. Each one ends with a check that proves it works. Don't start a phase until the one before it passes.

Phases 0 to 5 · the money flow
6 · Node SDK
7 · dashboard
Phase 0

Project setup

Build
Folder structure, TypeScript, an Express server, Prisma talking to a SQLite file.
Learn
How a Node project is laid out, what a database migration is.

Done when GET /health returns { ok: true }.

Phase 1

Merchants and API keys

Build
Merchant sign-up. Generate a public key and a secret key. Store only a hash of the secret. Middleware that reads Authorization: Bearer.
Learn
Why you hash secrets, how API authentication works.

Done when a request with a wrong key gets 401.

Phase 2

Create a payment

Build
POST /v1/payments. Check the input, save a pending transaction, return a checkout link.
Learn
Input validation, why tx_ref must be unique.

Done when sending the same tx_ref twice returns 409.

Phase 3

Checkout page and fake bank

Build
The page customers see. A card form, the fake bank's rules, an OTP step, then a redirect to the configured callback URL.
Learn
State machines, why card numbers never get saved.

Done when the decline test card marks the transaction failed.

Phase 4

Verify endpoint

Build
GET /v1/transactions/:id/verify. A merchant can only see their own transactions.
Learn
Why the redirect can't be trusted, access control.

Done when merchant B asking about merchant A's payment gets 404.

Phase 5

Webhooks

Build
Sign each webhook with HMAC, send it, retry after 1, 5 and 30 minutes on failure, log every attempt.
Learn
Message signing, retries, handling the same event twice.

Done when a correct signature passes and a tampered body fails.

Phase 6

Node SDK

Build
A package merchants install: payments.create(), transactions.verify(), webhooks.verify().
Learn
Designing a library other developers use, typed errors.

Done when an SDK example creates a payment against the running API, the checkout accepts a test card, and verification returns the expected status, reference, amount and currency. Integration tests check webhook signatures and duplicate delivery handling.

Phase 7

Merchant dashboard

Build
Log in, see transactions, see webhook attempts, set the webhook URL, replace a leaked key.
Learn
Sessions and cookies, building pages from server data.

Done when a replaced secret key stops working straight away.

Later, if you want

Decisions I made

Calls you can change

You didn't pick a language or tools, so I picked these. Tell me if any feel wrong.

TypeScript everywhereOne language for server, SDK and pages. The type checker catches mistakes before you run the code.
ExpressThe most common Node web framework. Most tutorials and Stack Overflow answers use it.
SQLite + PrismaThe database is one file. Nothing to install. Prisma's schema file reads like plain English.
HMAC-signed webhooksFlutterwave sends the same fixed password with every webhook. I'd sign each message instead, the way Paystack and Stripe do. It's safer and teaches you more.
Naira onlyMulti-currency adds exchange rates and rounding rules. Skip it for now.
Runs on your machineNo hosting until it all works locally. Deploying can be a later phase.
Out of scope

Not building

  • A demo shop or separate merchant application
  • Anything with real money, real cards or real banks
  • Bank transfer, USSD and mobile money payment options
  • Fraud checks, KYC and business verification
  • Settlements, fees and payouts (maybe as a stretch goal)
